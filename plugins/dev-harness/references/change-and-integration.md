# 变化与集成

收到新输入时先区分：新想法是提议，事实修正更新理解，已确认的目标变化调整执行。API key 等运行材料按安全配置使用，不把它当需求变更，不写入任务正文。

同一目标的细化更新原任务；新的独立目标另建或关联现有任务。探索允许保留假设与反例，不补造完整 PRD。实现与已确认需求不一致时先核对哪一方需要纠正，不能仅因代码已写就擅自改需求。

影响公共约定或其他在途工作时，在既有任务/决定入口记录：

- 新的行为或决定及其来源，替代的旧决定。
- 受影响的任务、接口和候选；哪些继续、哪些调整、哪些等待真实前提。
- 负责接续的人、集成目标与顺序；未知项明确保留。

这些是必要内容，不强制新建表单或编号体系。已获授权的技术调整自主推进；只有未确定且影响结果的业务取舍才需用户裁决。

MR 准备与集成前重新读取相关任务和目标分支：确认依赖是否已经进入目标、接口约定是否改变、base/head 与审查证据是否对应。不同文件也可能有依赖；文本合并成功不等于业务兼容。目标或关键依赖更新时，只重查受影响证据，并保留旧报告原来的适用范围。

核对集成结果时分别取得审查候选、平台 MR 快照、实际源分支 head 和目标中的集成提交。merged 只证明平台处理了它所记录的候选；源分支若继续前进，列出尚未纳入的工作，或指出由谁确认不纳入。平台仍在计算或快照不一致时先读取现状，不盲重试合并。

用平台记录和 Git 提交关系核实结果；squash/rebase 等方式不能仅靠原提交是否为祖先判断，要按项目采用的合并方式核对对应变更。只有声明范围已进入目标且适用门禁有证据，才按该范围报告集成完成；旧候选通过不覆盖后续变更。

一项工作可有多个 MR，一个 MR 可关联多项工作；探索结论不要求生成 MR。按平台现有机制维护关联，避免由每个 Agent 私设一份共享的“当前分支”。
